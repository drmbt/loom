# SPEC-VN — drmbt contributor board

Vincent Naples' (drmbt) working board for contributions to Loom. It exists so contributor
work never mints numbers in `SPEC.md`, which the upstream main session owns.

- **Prefix:** tasks are `VN<n>`, bugs are `VNB<n>`. Numbers are never reused.
- **Upstream rows are cited, never copied.** If upstream already tracks something, the row
  here is a pointer (`→ T1456b`) and the work happens there.
- **Commit subjects carry the VN id**, e.g. `VN1: Save as component on the canvas menu`.
- **A pull request description repeats its row**, so upstream can file it under a canonical
  T/B number if it wants one.
- Status: `.` open · `~` in progress · `x` landed (with commit hash) · `?` needs a
  reproduction before it is a task · `→` tracked upstream.

Source of the first batch: a hands-on session on 2026-10-03 (hosted build + local clone).

RULING (Vincent, 2026-10-05): a file handle the user gave Loom is the consent to use it.** The check handler (`src/desktop/file-permissions.cjs`, `fileGrant`) grants `fileSystem` read and write to Loom's own origin for an absolute path to a FILE; directories, other origins and protected OS paths (`file-system-access-restricted`) stay refused. The consent dialog behind the request handler was unreachable in Electron 44 and is gone; a `fileSystem` request that does arrive is refused without a prompt. Price, stated in the code: a file chosen in an earlier session reopens without asking, like a desktop app's recent files. Second finding, measured: a `fileSystem` CHECK in 44.5.1 carries NO webContents and no `requestingUrl`, only the requesting origin as a URL and the file details, so the old unit test's fake (contents + requestingUrl) matched nothing Electron sends. Proof: `src/desktop/testing/file-access.test.cjs`, run with `./node_modules/.bin/electron src/desktop/testing/file-access.test.cjs`, puts the real handlers on a real Electron session and drives real handles (CDP drop, then IndexedDB restore after a reload). It failed 3/7 before the fix with the reported symptom (`denied`, NotAllowedError) and passes 7/7 after; the origin guard is red-verified. `file-permissions.test.cjs` rewritten to the measured shape; `desktop:check` 146/146; gates green. Original report: the desktop app could not read ANY local file through a file handle (Movie File In, Audio File In, mesh files; "Allow access" flickered and did nothing); cause measured with `scratchpad/fsa-probe/main.cjs`: once a session has a permission CHECK handler, Electron answers a file handle's status from that handler alone, granted or denied, never "prompt" (undefined and null read as denied, a throw hangs Electron), and Loom's check returned false for `fileSystem`, so the request handler and its dialog were never reached.|T1329, T1519b, V220
VNB6|x|**LANDED `12200545` on `drmbt`: the editing hook registers a forwarding `runtime.resetFeedback` on each component session bus, addressed to the viewed instance's flattened ids.** Original report: a Reset pulse fired INSIDE a component is refused: `Pulse "resetPulse" fires "runtime.resetFeedback", which no track has registered.`** Reported 2026-10-04. Cause, from the code: Feedback, Echo, Cache and Slit Scan declare a `resetPulse` that fires `runtime.resetFeedback`; `parameter.pulse` asks the bus it runs on whether that command exists (`parameter-commands.ts`). The app registers it on the ROOT bus only (`useRuntimeCommands`, `app.tsx`). Diving into a component edits through a separate session bus (`openComponentSession`, `session.ts`), which registers component commands and nothing from the runtime, so every reset button inside a component refuses. Fix shape: the editing layer registers a forwarding `runtime.resetFeedback` on the session bus that addresses the viewed instance's flattened ids (`<instance>/<node>`) on the root bus — T1541b's rule, a pulse inside a definition acts on its instance. Reproduced as a test that fails with the reported sentence; not yet pressed by hand in the running app.|T1541b, V123, V220
VNB7|x|**LANDED `2974a9c5` on `drmbt`; confirmed live in `pnpm desktop:dev` with Arena. Syphon In never received Resolume Arena.** Sources listed and opened, but every acquire threw `Syphon source IOSurface is not tested packed BGRA8`, so the node waited forever on "Waiting for a native video frame". Measured with the real addon against Arena's two live servers: the surfaces are fourcc 0 (unset), 4 bytes/element, no planes, 7680-byte rows at 1920x1080, wrapped by SyphonMetalClient as BGRA8Unorm. Current Syphon stamps 'BGRA' (`SyphonServerBase.m`); the older OpenGL servers still embedded in shipping apps leave it unset, and Syphon's own client ignores the fourcc (`SyphonMetalClient.m`), which is why TouchDesigner showed the feed. `syphon-input.mm` now accepts fourcc 'BGRA' or unset when the surface is otherwise packed 4-byte BGRA; any other fourcc, element size or a planar surface is still refused. Proof: the fixed addon pulled 107-110 frames in 2 s from each Arena server with no errors, copied frames read as real picture (mean level ~130/255, 98% non-black); `testing/syphon-input.test.cjs` still passes (20 assertions). No committed regression test: the pinned framework cannot publish an unstamped surface, so a fixture would mean reimplementing the Syphon server protocol. The addon is rebuilt at every `pnpm desktop:dev` launch.|T1341
